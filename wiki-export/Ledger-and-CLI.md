# Ledger and CLI

## Why a ledger exists at all

`pocket-dating-coach` already owns the numeric ledger — spend, clicks, views, signups. What it has no
memory of is *why* a given ad set exists: which recommendation produced it, what the reasoning was,
whether what actually got built matched the brief. That's what this repo's ledger records.

## Format

One markdown file per campaign recommendation, at `campaigns/<slug>/record.md` — a YAML front-matter
block (machine-readable: status, IDs, dates, budget) followed by a body that accumulates a new section
at each lifecycle stage. Chosen over plain JSON (unreadable at a glance — this ledger has a human
reader as well as an agent one) and over a spreadsheet (nothing to build around; unlike `job-hunt-agent`
there was no pre-existing habit like a Career Hacking Tracker to inherit).

`INDEX.md` at the repo root is generated — regenerated by every command that changes the ledger — and
is the human-facing at-a-glance table. Never hand-edit it.

## Lifecycle

```
proposed → executing → live → reviewed
              ↓
          abandoned
```

- **proposed** — `ad-agent propose` was run; a recommendation exists, nothing has been built yet.
- **live** — `ad-agent log-setup` was run with the real campaign/ad-set/ad IDs from Ads Manager.
- **reviewed** — `ad-agent log-review` was run with a verdict from the audit mode.
- **abandoned** — `ad-agent abandon` was run because the proposal was never going to be executed.

## Command reference

`ad-agent propose <slug> --network snap|meta --campaign-name ... --ad-set-name ... --ad-name ... --targeting-summary ... --creative-ref ... --budget-cap <INR/day> --duration-days <n> --brief <path>`
Records a new recommendation. Prints the generated `rec_id`.

`ad-agent log-setup <rec_id> --network ... --campaign-id ... --ad-set-id ... --ad-id ... [--deviated "..."]`
Records what was actually built. The `ad-set-id` recorded here is deliberately the same join key
`pocket-dating-coach`'s own analytics use internally (`network:ad_set_id`), so the audit mode never has
to hand-attach performance data later.

`ad-agent log-review <rec_id> --verdict working|not-working|inconclusive --summary "..." [--review-log <path>]`
Records the audit mode's finding against a live recommendation.

`ad-agent abandon <rec_id> --reason "..."`
Closes out a recommendation that was never executed, so it doesn't sit as `proposed` forever.

`ad-agent stats`
Deterministic counts — how many proposed / live / reviewed / abandoned, and a verdict breakdown.

`ad-agent dump-ledger [--status live|proposed|reviewed|abandoned]`
Prints the index table, optionally filtered.

`ad-agent fetch-analytics --start <date> --end <date> [--network ...] [--audience ...] [--out <path>]`
Pulls real performance data — see [Data Access](Data-Access). Not functional until the
`pocket-dating-coach` side of that is built.

## Nothing here calls an LLM

Every one of these commands is a deterministic file read/write, or in `fetch-analytics`'s case, one
plain HTTP call. The actual thinking that produces the `--targeting-summary`, the brief, the verdict —
all of that happens in the Claude Code session before the CLI is ever invoked.
